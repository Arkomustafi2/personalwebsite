📅 Study Plan — Block Cipher Modes of Operation

What This Topic Is Really About

A block cipher (e.g., AES, DES) encrypts a fixed-length block (e.g., 64 or 128 bits) at a time. When real-world messages are longer, we must decide how to chain or process multiple blocks — these strategies are called modes of operation. The five standard modes (ECB, CBC, CFB, OFB, CTR) differ in how the output of one block affects subsequent blocks, trading off security, parallelizability, error propagation, and suitability for different use cases. XTS-AES is a specialized mode for storage-layer encryption, not transmission. Understanding these modes means understanding where block ciphers fail or succeed in real deployments.

🔐 ECB & CBC — Block-Oriented Modes

Why Modes of Operation Exist

A block cipher (e.g., AES-128) encrypts exactly b-bit inputs to b-bit outputs. Real messages are longer. The solution: partition plaintext into b-bit blocks (pad the last block if necessary) and apply the cipher to each block. The manner in which this is done determines security properties — different modes of operation have been developed to address different security issues arising from naive block-by-block encryption.

Key Concept
If you just encrypt each block independently with the same key (ECB), identical plaintext blocks produce identical ciphertext blocks — a catastrophic pattern-leakage vulnerability.
ECB — Electronic Codebook Mode

Mechanism

Each b-bit plaintext block is encrypted independently using the same key K. The blocks have no relationship to each other.

ECB Encryption: C_i = E(K, P_i) for i = 1, 2, ..., N ECB Decryption: P_i = D(K, C_i) for i = 1, 2, ..., N

Step-by-Step Encryption Trace

1
Partition plaintext M into N blocks of b bits each: P_1, P_2, ..., P_N (pad P_N if |M| mod b ≠ 0)
2
Apply the block cipher E with key K to each block independently: C_i = E(K, P_i)
3
Concatenate ciphertext blocks: C = C_1 || C_2 || ... || C_N
4
Decryption is the exact reverse — each C_i decrypted independently with D(K, ·)
P_1 P_2 ... P_N | | | K→ [Encrypt] K→ [Encrypt] ... K→ [Encrypt] | | | C_1 C_2 ... C_N

Properties & Security Analysis

PropertyECB Behavior
Block Size64-bit blocks (DES context from slides)

Parallelism (Dec)Yes — fully parallel

Exam Critical
ECB's fundamental flaw: With long messages, repetition in plaintext causes repetition in ciphertext. An attacker can detect repeated blocks, infer structure, and perform replay attacks — even without knowing the key. The famous "ECB penguin" image demonstrates how ECB preserves pixel-block patterns.
Typical Application
Secure transmission of single isolated values (e.g., one AES session key). Never use for bulk data encryption.
CBC — Cipher Block Chaining Mode

Core Idea

CBC solves ECB's pattern-leakage problem by XOR-ing each plaintext block with the previous ciphertext block before encryption. This chains the blocks — each ciphertext block depends on all previous plaintext blocks. A random Initialization Vector (IV) seeds the first block.

CBC Encryption: C_i = E(K, P_i ⊕ C_{i-1}) where C_0 = IV CBC Decryption: P_i = D(K, C_i) ⊕ C_{i-1} where C_0 = IV

Step-by-Step CBC Encryption

1
Choose a random IV of b bits. This is C_0 for the first iteration. IV must be known to both sender and receiver but kept secret from the attacker.
2
XOR the first plaintext block P_1 with IV: PP_1 = P_1 ⊕ IV
3
Encrypt: C_1 = E(K, PP_1) = E(K, P_1 ⊕ IV)
4
For each subsequent block i ≥ 2: XOR P_i with C_{i-1}, then encrypt: C_i = E(K, P_i ⊕ C_{i-1})
5
Continue until all N blocks processed. Output: C_0 (IV) || C_1 || C_2 || ... || C_N
IV C_{i-1} ... C_{N-1} | | | ⊕←P_1 ⊕←P_2 ⊕←P_N | | | K→[Encrypt] K→[Encrypt] ... K→[Encrypt] | | | C_1───────→ C_2───────→ ... C_N

Step-by-Step CBC Decryption

1
Decrypt C_i using D(K, ·) to get an intermediate value
2
XOR with the previous ciphertext block C_{i-1} (or IV for i=1): P_i = D(K, C_i) ⊕ C_{i-1}
3
Crucially, since C_{i-1} is already received (it's ciphertext), ALL blocks can be decrypted simultaneously in parallel — decryption is fully parallelizable.
Exam Critical — Asymmetry
CBC encryption is inherently sequential (you need C_{i-1} to compute C_i). But CBC decryption is fully parallelizable (all C_i are already available; you just need D(K, C_i) and C_{i-1} for each block independently).

CBC Error Propagation Analysis

Error LocationEffect on Decryption
Single-bit error in C_iCorrupts entire P_i AND exactly one bit in P_{i+1} (the same bit position). P_{i+2}, P_{i+3}, ... unaffected.
Error in IVOnly P_1 is affected; all subsequent blocks decrypt correctly
Lost/inserted block in C_iAll subsequent blocks are garbled (loss of sync)
Key Property — Self-Synchronizing
If a ciphertext block is corrupted, the error affects only 2 consecutive plaintext blocks (C_i corrupts P_i and P_{i+1}). The cipher re-synchronizes from C_{i+1} onward — this is called self-synchronization or a limited error-propagation window.

CBC Feedback Architecture (from Slide 18)

In CBC, the output register (ciphertext) feeds back as input to the next XOR before encryption:

CBC Feedback Path (one unit): Plaintext block → ⊕ → Input Register → [Encrypt] → Output Register → Ciphertext ↑ | └──────────────── C_{i-1} (feedback from output) ─────────────┘

This is ciphertext feedback: the previous ciphertext block is what gets XOR'd with the next plaintext block.

🌊 CFB & OFB — Stream-Oriented Modes

CFB — Cipher Feedback Mode

CFB converts a block cipher into a stream cipher. Instead of waiting for a full b-bit block, CFB processes s bits at a time (where s ≤ b). A shift register maintains state. This eliminates the padding requirement.

CFB Mechanism — Shift Register Detail

1
Initialize the b-bit shift register with IV (e.g., b = 64, s = 8).
2
Encrypt the shift register contents: O = E(K, ShiftReg) — producing b bits of output.
3
Select the leftmost s bits of O; discard the remaining (b−s) bits.
4
XOR the s selected bits with the s-bit plaintext segment P_i: C_i = MSB_s(E(K, ShiftReg)) ⊕ P_i
5
Shift the register left by s positions; insert C_i (the ciphertext) into the rightmost s bits. This is the critical feedback step.
6
Repeat from step 2 for the next s-bit segment.
CFB Encryption: C_i = MSB_s(E(K, X_i)) ⊕ P_i CFB Decryption: P_i = MSB_s(E(K, X_i)) ⊕ C_i where X_i is the shift register state (b bits): X_1 = IV X_{i+1} = LSB_{b-s}(X_i) || C_i (shift left s bits, insert C_i)
CFB Encryption (one stage, b=64, s=8): ┌── Shift Register: [b-s bits | s bits] ──┐ │ ↑ C_{i-1} inserted │ │ │ K→ [Encrypt] │ | │ [Select s bits] [Discard b-s bits] │ | │ ⊕ ← P_i (s bits) │ | │ C_i (s bits) ─────────────────────────┘ (feedback) → transmitted
Exam Critical — Why Decryption Uses E(K, ·) Not D(K, ·)
In CFB decryption, the shift register still feeds through Encrypt, not Decrypt. This is because the XOR keystream is generated identically on both sides — we XOR C_i with the same keystream to recover P_i. The encryption operation is inverted by XOR, not by calling the inverse cipher function.

Error in C_iImpact

Total corruption window1 + ⌈b/s⌉ consecutive s-bit segments. For b=64, s=8: 1 + 8 = 9 bytes affected.

Key Insight
CFB is essentially a synchronous stream cipher where the keystream is derived from previous ciphertext (via the shift register). This makes it self-synchronizing after an error — after b/s steps, the error clears.
OFB — Output Feedback Mode

OFB is structurally similar to CFB but with one critical difference: the feedback comes from the encryption output (keystream), not from the ciphertext. This decouples the keystream from the message, enabling pre-computation.

OFB Encryption: O_i = E(K, O_{i-1}) where O_0 = Nonce (IV) C_i = P_i ⊕ O_i OFB Decryption: O_i = E(K, O_{i-1}) (identical — keystream is same) P_i = C_i ⊕ O_i

Step-by-Step OFB Operation

1
Initialize the b-bit input register with Nonce (a unique value per message, analogous to IV).
2
Compute keystream output: O_1 = E(K, Nonce)
3
XOR with plaintext: C_1 = P_1 ⊕ O_1
4
Feed O_1 (the encryption OUTPUT — NOT C_1) back as input for next step: O_2 = E(K, O_1)
5
The keystream {O_1, O_2, O_3, ...} can be computed entirely before seeing any plaintext, since it depends only on (K, Nonce).
OFB vs CFB — The Critical Difference: CFB feedback: C_i ───────────→ [Shift Register] → E(K,·) → keystream (ciphertext feeds back — message-dependent) OFB feedback: O_i = E(K,·) → [Shift Register] → E(K,·) → keystream (encryption output feeds back — message-independent)

OFB Error Propagation

Exam Critical — OFB Error Behavior
Because OFB feedback is independent of ciphertext, a bit error in C_i corrupts only P_i (the corresponding bit). There is NO error propagation to subsequent blocks. However, OFB is more vulnerable to message stream modification attacks — if an attacker knows the plaintext and can flip bits in C_i, they can predictably modify the corresponding plaintext bits.

⚡ CTR & XTS-AES — Modern Parallelizable Modes

CTR — Counter Mode

CTR converts a block cipher into a stream cipher using a counter as input to the encryption function. The counter is typically initialized with a nonce and incremented for each block. CTR achieves full parallelism for both encryption and decryption.

CTR Encryption: C_i = E(K, Counter_i) ⊕ P_i CTR Decryption: P_i = E(K, Counter_i) ⊕ C_i Counter_i = Counter_1 + (i - 1) (simple increment, or any non-repeating sequence)

CTR Encryption Step-by-Step

1
Choose N unique counter values Counter_1, Counter_2, ..., Counter_N (typically Counter_1 = Nonce, Counter_{i+1} = Counter_i + 1). Counter values must never repeat for the same key.
2
For each block i, independently compute: keystream_i = E(K, Counter_i)
3
XOR with plaintext block: C_i = keystream_i ⊕ P_i
4
Because each counter block is independent, all N blocks can be processed simultaneously in parallel on multi-core hardware.
5
Decryption is identical: P_i = E(K, Counter_i) ⊕ C_i. No inverse cipher needed.
Counter_1 Counter_2 ... Counter_N (inside dashed box) | | | K→[Encrypt] K→[Encrypt] ... K→[Encrypt] | | | ⊕←P_1 ⊕←P_2 ⊕←P_N | | | C_1 C_2 ... C_N Note: No arrows between stages — complete independence!
Exam Critical — CTR Unique Properties
CTR is the only mode here where both encryption and decryption are fully parallelizable. This is because each block's keystream depends only on (K, Counter_i), not on any other block's output. CTR also allows random access — you can decrypt any block C_i without processing earlier blocks.

Parallelism (Enc)Yes — fully parallel
Parallelism (Dec)Yes — fully parallel

Key Point — CTR vs OFB
Both CTR and OFB produce keystreams independent of plaintext. In OFB, keystream block i depends on keystream block i−1 (sequential). In CTR, each keystream block depends only on its counter (parallel). CTR strictly dominates OFB in performance without any security loss.
XTS-AES — Encryption for Stored Data

XTS-AES (XEX-based Tweaked-codebook mode with ciphertext Stealing) is designed specifically for encrypting stored data on block devices (disk sectors, flash blocks), as opposed to transmitted data. It uses two independent AES keys and a mathematical tweak per block position.

Context
Storage encryption has a unique constraint: the ciphertext must be exactly the same size as the plaintext (no expansion), because disk sectors have fixed sizes. XTS-AES achieves this while providing sector-level context binding.

XTS-AES Single-Block Encryption — Step by Step

1
Compute Tweak T: Given sector index i and block position within sector j, compute the tweak value: T = E(Key₂, i) ⊗ α^j — where ⊗ is multiplication in GF(2^128), and α is a primitive element (the polynomial x, i.e., α = 0x02 in GF(2^128)).
2
Pre-whiten plaintext: PP = P_j ⊕ T (XOR plaintext block with the tweak)
3
Core encryption: CC = E(Key₁, PP) — encrypt the pre-whitened plaintext using Key₁
4
Post-whiten ciphertext: C_j = CC ⊕ T (XOR again with the same tweak)
XTS-AES Single Block Encryption: T = E(Key₂, i) ⊗ αʲ (tweak for sector i, block j) PP = P_j ⊕ T (pre-whitening) CC = E(Key₁, PP) (AES encryption with Key₁) C_j = CC ⊕ T (post-whitening) XTS-AES Single Block Decryption: T = E(Key₂, i) ⊗ αʲ (same tweak computation) CC = C_j ⊕ T (undo post-whitening) PP = D(Key₁, CC) (AES decryption with Key₁) P_j = PP ⊕ T (undo pre-whitening)

XTS-AES Full Sector Encryption

1
For a sector containing blocks P_0, P_1, ..., P_{m-1}, P_m (where P_m may be a partial/incomplete block): encrypt P_0 through P_{m-2} using the standard XTS block procedure with tweak (i, 0), (i, 1), ..., (i, m-2).
2
Last full block P_{m-1}: Encrypted with tweak (i, m). Output XX (intermediate full-block ciphertext). The final partial ciphertext C_m is composed of the most significant bits of XX (as many as P_m has).
3
Ciphertext Stealing for partial block P_m: The partial plaintext P_m is concatenated with the least significant bits of XX (those that were "excess" from XX) to form a full b-bit block CP. Encrypt CP with tweak (i, m-1) to get C_{m-1}.
4
Final output: C_0, C_1, ..., C_{m-2}, C_{m-1}, C_m — same total byte count as the input sector (no expansion).
Exam Critical — XTS-AES Design Rationale
The "tweak" T = E(Key₂, i) ⊗ αʲ serves as a per-block context binding. Two keys are used: Key₂ derives the sector-specific tweak, Key₁ encrypts the actual data. This prevents cross-sector attacks — the same plaintext at different sectors/positions produces different ciphertext. The GF(2^128) multiplication by αʲ cheaply generates j distinct tweaks per sector from one AES operation.
