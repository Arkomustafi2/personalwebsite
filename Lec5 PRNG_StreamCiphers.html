📌 What This Lecture Is Really About

Cryptography depends on unpredictable sequences of bits. This lecture establishes how those sequences are generated: starting from physical entropy (TRNG), converting it into a scalable pseudo-random stream (PRNG), and applying that stream to encrypt data one byte at a time (stream ciphers). You will study three PRNG constructions — the Linear Congruential Generator, the Blum Blum Shub generator, and block-cipher-based PRNGs — then dissect RC4, the dominant stream cipher in legacy wireless and web protocols. The central insight is the tradeoff between computational security and true unpredictability.

⚠ Exam FocusKnow the BBS algorithm cold (formula + why it's cryptographically secure), understand the RC4 KSA and PRGA pseudocode step-by-step, and be able to distinguish TRNG vs PRNG vs PRF with architectural diagrams.

🎲 Uses of Random Numbers in Cryptography

🔑 Three Primary Uses 1. Key distribution and authentication schemes
2. Generation of session keys or keys for RSA
3. Generation of the bit stream for stream ciphers
ℹ NoteEvery cryptographic protocol ultimately depends on the quality of its random number source. A weak RNG breaks the entire system regardless of algorithm strength.

📊 Properties of Random Numbers

Randomness

PropertyDefinitionTest Examples
Uniform DistributionFrequency of 0s and 1s are approximately equal across the sequenceFrequency test, monobit test
IndependenceNo sub-sequence can be statistically inferred from knowledge of other sub-sequencesRuns test, serial test, autocorrelation

Unpredictability

⚠ Exam CriticalUnpredictability means it is computationally hard to predict the next value in the sequence — even when you know the algorithm and have observed previous outputs. This is stronger than just randomness.
Forward UnpredictabilityGiven outputs k₁, k₂, …, kₙ, it is infeasible to predict kₙ₊₁
Backward UnpredictabilityGiven outputs kₙ, kₙ₊₁, …, it is infeasible to determine previous values or the seed

📌 PipelineIn practice: TRNG generates a truly random seed → that seed is fed into a PRNG → the PRNG produces a scalable pseudorandom bit stream. This combines the unpredictability of hardware entropy with the efficiency of algorithmic generation.

⚙️ TRNG Sources

Physical Phenomena Used

  • Ionizing radiation event detection
  • Leaky capacitors (hardware noise)
  • Thermal noise from resistors
  • Audio input noise
  • Mouse/keyboard activity timing
  • I/O operation timing jitter
  • OS interrupt timing
⚠ LimitationTRNGs produce only a small number of values per second. They cannot directly supply the high-bandwidth random bit streams needed by stream ciphers. This is why they are used only to seed PRNGs.
Modern NoteIntel CPUs include RDRAND/RDSEED hardware instructions that mix TRNG entropy with AES-CTR PRNG to provide fast, secure random numbers at CPU speed.

📋 PRNG Requirements Summary

1
Randomness — The output must pass statistical tests for uniformity, scalability, and consistency. Key tests: frequency test (equal 0/1 distribution), runs test (lengths of runs of identical bits), compressability test.
2
Unpredictability — Both forward and backward unpredictability must hold. Even an adversary who knows the algorithm and has seen many outputs must be unable to predict future or past values.
3
Secure Seed — The seed itself must be unpredictable. The standard solution is to generate the seed using a TRNG. If the seed is compromised, the entire PRNG output is compromised.
⚠ Core Principle"Hard to determine pseudo-random stream if you don't know the seed — but do know the algorithm." Security rests entirely on seed secrecy, not algorithm secrecy (Kerckhoffs's principle).

📐 Linear Congruential Generator (LCG)

Parameters

ParameterSymbolConstraintDescription
Modulusmm > 0Sets the range of output values [0, m−1]
Multipliera0 < a < mScaling factor
Incrementc0 ≤ c < mAdditive constant (0 = multiplicative congruential)
SeedX₀0 ≤ X₀ < mInitial value

Recurrence Formula

X_{n+1} = (a·X_n + c) mod m Generate sequence: {X₀, X₁, X₂, X₃, ...}

Parameter Selection Rules

🔑 Key Choices • m should be large and prime. A common choice: m = 2³¹ − 1 = 2,147,483,647
• If c = 0 (multiplicative form), good values of a are limited. Example: a = 7⁵ = 16807
• The Hull-Dobell theorem gives conditions for full period m
⚠ Critical WeaknessIf an attacker knows the parameters (m, a, c) AND observes even one output value X_n, they can compute ALL subsequent values X_{n+1}, X_{n+2}, ... trivially. LCG is NOT cryptographically secure. It is used for simulation, not encryption.

🔐 Blum Blum Shub (BBS) Generator

Parameters & Setup

1
Choose p, q: two large prime numbers such that p ≡ q ≡ 3 (mod 4). This congruence condition is critical for the security proof.
2
Compute n = p × q. This is a Blum integer. Factoring n must be infeasible for security.
3
Choose s: a random number relatively prime to n (i.e., gcd(s, n) = 1). This is the seed.

Generation Algorithm

X₀ = s² mod n ← Initial state (seed squared) for i = 1 → ∞: X_i = (X_{i-1})² mod n ← Square previous state B_i = X_i mod 2 ← Output bit = LSB of X_i
🔑 Security BasisBBS is cryptographically secure under the assumption that factoring large integers is computationally intractable (equivalent to the Quadratic Residuosity Problem). Even with all outputs B₁, B₂, …, Bₙ, determining the seed or predicting Bₙ₊₁ is as hard as factoring n.
OutputOnly the least significant bit (parity) of X_i is output as B_i. This extreme restriction is what makes BBS provably secure. One bit per iteration means it is slow but cryptographically strong.

🔲 PRNG Based on Block Ciphers

Use symmetric block ciphers (AES, DES) to produce pseudorandom bits. The seed consists of the encryption key K and a value V that is updated each round.

Counter (CTR) Mode

V = 1 loop: V = V + 1 ← Increment counter output = E_K(V) ← Encrypt counter pseudorandom_bits ← output
Mechanism V starts at 1 and is incremented each iteration. The counter value is encrypted with key K to produce pseudorandom output. V feeds back into itself via the +1 operation.

Output Feedback (OFB) Mode

V = initial_value loop: output = E_K(V) ← Encrypt current V V = output ← New V = output pseudorandom_bits ← output
Mechanism V is the current state. After each encryption, V is replaced by the output. Unlike CTR, the feedback is from the cipher output rather than a counter.
PropertyCounter ModeOFB Mode
V UpdateV = V + 1 (arithmetic)V = E_K(V) (cipher feedback)
ParallelizableYesNo (serial dependency)
Error propagationLocalizedLocalized

🏛️ ANSI X9.17 PRNG

A cryptographically secure PRNG standardized by ANSI, using Triple DES (3DES). Historically used in financial applications and PGP key generation.

Inputs

InputSymbolSizeRole
Date/time representationDT_i64-bitTimestamp that changes each call — ensures different output even with same seed
Seed valueV_i64-bitInternal state, updated every round
Key pairK₁, K₂2 × 56-bit DESUsed in Triple DES (EDE) operations

Operation — Three Triple-DES Steps

1
Encrypt the timestamp: Compute EDE(K₁K₂, DT_i) to get an intermediate value. EDE = Encrypt with K₁, Decrypt with K₂, Encrypt with K₁ (Triple DES).
2
Generate R_i: XOR the result from step 1 with V_i, then apply EDE again: R_i = EDE(K₁K₂, EDE(K₁K₂, DT_i) ⊕ V_i). R_i is the 64-bit pseudorandom output.
3
Update V_{i+1}: XOR R_i with the step-1 intermediate, then apply EDE: V_{i+1} = EDE(K₁K₂, R_i ⊕ EDE(K₁K₂, DT_i)). This updates the seed for the next call.

Outputs

R_i — 64-bit pseudorandom number output to the application
V_{i+1} — 64-bit updated seed for the next iteration
⚠ Why Three EDE Operations? The first EDE ensures DT_i is unpredictably mixed. The second produces the output R_i. The third regenerates V to ensure backward unpredictability — knowing R_i should not let you recover V_i.

🌊 Stream Ciphers — Core Concept

A stream cipher encrypts plaintext one byte (or bit) at a time by XOR-ing it with the corresponding byte of a pseudorandom keystream. Both sender and receiver must use the same key K and thus generate identical keystreams.

Encryption: C = M ⊕ k (ciphertext = plaintext XOR keystream byte) Decryption: M = C ⊕ k (plaintext = ciphertext XOR keystream byte) Key: K → Keystream Generator → k₁ k₂ k₃ k₄ ... ↓ ↓ ↓ ↓ Plaintext: M₁ M₂ M₃ M₄ ... Ciphertext: C₁ C₂ C₃ C₄ ...
🔑 Why XOR works for decryption: (M ⊕ k) ⊕ k = M ⊕ (k ⊕ k) = M ⊕ 0 = M. XOR is its own inverse when the same keystream is used.
⚠ Critical Security RuleNEVER reuse the same key K (and thus the same keystream) for two different messages. If C₁ = M₁ ⊕ k and C₂ = M₂ ⊕ k, then C₁ ⊕ C₂ = M₁ ⊕ M₂ — the key is eliminated and the messages can be recovered. This destroyed WEP.

🎯 Design Criteria for Stream Ciphers

Requirements

Large Period The encryption sequence (keystream) must have a very large period before it repeats. Repeating keystream = catastrophic vulnerability.
Approximate True Randomness The keystream must be statistically indistinguishable from a true random sequence. Must pass all NIST randomness tests.
Long Key The key must be long enough to withstand brute force attacks. Minimum 128 bits for security today.

📡 RC4 — Background & Properties

History • Designed by Ron Rivest at RSA Security in 1987
• Initially a trade secret; source code leaked in 1994
• Used in SSL/TLS (until 2015), WEP, WPA (TKIP)
Key Properties • Variable-size key: 8 to 2048 bits (slides say 8–2048; algorithm uses 1–256 bytes)
• Very simple and efficient implementation
• Software-efficient — no lookup tables beyond S-box
⚠ RC4 Security Status RC4 has several theoretical weaknesses:
• Key scheduling algorithm (KSA) has biases
• First few bytes of keystream are weakly random

Practical mitigation: Use 128-bit key + discard first 256 bytes of keystream → no known attacks

WEP failure was NOT RC4's fault — WEP reused IVs and used short keys incorrectly. The algorithm was fine; the protocol was broken.

⚙️ Phase 1: Key Scheduling Algorithm (KSA)

Step 1 — Initialize S and T

for i = 0 to 255 do S[i] = i ← S is identity permutation: [0, 1, 2, ..., 255] T[i] = K[i mod keylen] ← T is key repeated to fill 256 bytes
Intuition: S starts as the identity permutation. T is filled by cycling through the key bytes. If key length is 16 bytes, T = K₀K₁…K₁₅K₀K₁… (repeated 16 times).

Step 2 — Initial Permutation of S

j = 0 for i = 0 to 255 do j = (j + S[i] + T[i]) mod 256 Swap(S[i], S[j]) ← Mix S using T (key-dependent)
🔑 What this does: Performs 256 key-dependent swaps on S. After this loop, S is a complex permutation of {0,…,255} that is entirely determined by K. The same K always produces the same permuted S — this is the setup.
⚠ After KSA: S is a permutation (still contains all values 0–255, just reordered). T is discarded — it is only used during initialization. The security of RC4 depends entirely on how well K scrambles S.

⚙️ Phase 2: Pseudo-Random Generation Algorithm (PRGA)

i = 0; j = 0 while (true): i = (i + 1) mod 256 ← Advance i cyclically j = (j + S[i]) mod 256 ← Advance j based on S[i] Swap(S[i], S[j]) ← Swap to continuously evolve S t = (S[i] + S[j]) mod 256 ← Compute index t k = S[t] ← Output keystream byte C = p XOR k ← Encrypt p = C XOR k ← Decrypt
1
Advance i: i cycles through 0→1→2→…→255→0→… ensuring every S element is eventually used as the primary index.
2
Advance j: j depends on S[i], making the progression non-linear and key-dependent. j does NOT follow a fixed cycle.
3
Swap S[i] and S[j]: S is continuously modified after every byte output. This means the internal state evolves with each byte, unlike a simple fixed permutation cipher.
4
Output k = S[t]: t = (S[i] + S[j]) mod 256 is a third, indirect index into S. The output k is looked up at position t — not directly at i or j. This indirection prevents predicting k from i and j alone.
⚠ Why the state evolves: After 256 iterations, i has gone through a full cycle, but j has followed a complex, key-dependent path. S has been modified 256 times. The state space is approximately 256! × 256 × 256 — astronomically large, which is why RC4 has a very long period.

🧩 RC4 Full Algorithm Summary

KSA

1
S[i] = i for all i (identity)
2
T[i] = K[i mod keylen] for all i
3
j = 0
4
For i=0..255: j=(j+S[i]+T[i]) mod 256; Swap(S[i],S[j])

PRGA

1
i=0, j=0
2
i=(i+1) mod 256
3
j=(j+S[i]) mod 256
4
Swap(S[i], S[j])
5
t=(S[i]+S[j]) mod 256; k=S[t]
6
C = p ⊕ k; repeat from step 2
Security note: The entire state of RC4 can be described as the tuple (S, i, j) where S is 256 bytes and i, j are single bytes. That's 256 + 1 + 1 = 258 bytes of state, representing an incredibly large state space that makes RC4 hard to break by state enumeration.
