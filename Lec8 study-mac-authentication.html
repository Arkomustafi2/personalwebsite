Overview

What This Lecture Is Really About

Encryption alone does not protect against an adversary who modifies messages in transit — you can decrypt a tampered ciphertext and get a wrong but plausible-looking message. This lecture builds the separate concept of message authentication: proving that a message came from who you think, and that it has not been changed. The fundamental tool is the Message Authentication Code (MAC), a keyed function that produces a short tag which is computationally impossible to forge without knowledge of the secret key.

The lecture maps cleanly onto two themes: why we need MACs (the limits of symmetric encryption) and how we build them (block-cipher MACs like CMAC, and hash-based MACs like HMAC). Both themes have direct exam relevance, especially the security bound min(2^k, 2^n) and the HMAC construction formula.

Authentication Goals

What the Receiver Wants to Verify Exam

1 · Data Authentication

Contents of the message have not been modified between sender and receiver. Any bit-level change must be detectable.

2 · Source Authentication

The source of the message is who they claim to be. The message must have originated from the claimed sender.

Four Approaches: Symmetric Key Encryption · Message Authentication Codes (MACs) · Hash Functions · Public Key Encryption (Digital Signatures). This lecture focuses on MACs.
Symmetric Encryption for Authentication

How it Works & Why it Falls Short Key

A shares a secret key K with B. A sends E(K,M). B decrypts with same key K.

┌───┐ ┌────────────────┐ ┌───┐ │ M │ ──► (E) ──► │ E(K, M) │ ──► (D) ──► │ M │ └───┘ ↑ └────────────────┘ ↑ └───┘ K K Sender A Channel Receiver B
✓

Confidentiality: Only B (sharing key K with A) can recover the plaintext M.

✓

Source Authentication: A is the only other user with key K. So the ciphertext must have come from A.

✓

Data Authentication: If decryption succeeds and produces meaningful plaintext, the data has not been modified (a random modification would decrypt to garbage).

!

Critical Assumption: The decryptor must be able to recognise correct plaintext. This is not always possible — see the three examples below.

Key Takeaway: For binary or compressed data, symmetric encryption alone cannot provide reliable authentication. This is why MACs were invented — they provide a separate integrity guarantee that does not depend on recognising plaintext structure.

General principle: Valid plaintexts are only a small subset of all possible bit strings of length n. For messages of length n using a 26-character alphabet, there are 26ⁿ possible bit strings, but only a tiny fraction form valid English phrases. Adding structure (error-detecting codes, packet headers, frame check sequences) makes detection easier.

Definition

Message Authentication Code Key

A MAC appends a small, fixed-size block of data (a tag) to the message. This tag is computed by a function that takes both the message and a secret key:

T = MAC(K, M) M = input message (arbitrary length) MAC = the MAC function (also called a keyed hash function) K = shared secret key of k bits T = message authentication code (tag) of n bits
Unlike Encryption: MAC does not need to be reversible. A many-to-one function is fine — this makes it easier to design stronger MAC functions than encryption functions.
Alternate name: "keyed hash function." The key K controls which of many possible hash functions is used for that session.
Example Uses

Three MAC Configurations (Stallings Fig. 12.4) Exam

(a) Message Authentication Only

┌───┐ ┌───┐ │ M │──►(||)──────────────────► │ M │──►(C)──────►Compare └───┘ ↑ │tag│ ↑ │ ┌─────────┐ └───┘ K └───►│MAC(K,M) │═══════════════╝ K └─────────┘ Sender: Send M concatenated with MAC(K,M) Receiver: Recompute MAC with shared K, compare tags

Use case: Integrity + source auth, but no confidentiality. M is sent in the clear.

(b) Auth + Confidentiality (MAC tied to Plaintext)

┌───┐ ┌───┐ │ M │──►(||)──►(E) ──► E(K₂,[M||C(K₁,M)])──►(D)──► M ──►(C)──►Compare └───┘ ↑ ↑ ↑ ↑ │ K₂ ↑ MAC(K₁,M) computed K₂ K₁ └────(C)◄─K₁ on plaintext first Key insight: MAC is computed on plaintext, then the whole thing is encrypted. Two keys: K₁ for MAC, K₂ for encryption.

Use case: Confidentiality + integrity. Receiver decrypts first, then verifies MAC.

(c) Auth + Confidentiality (MAC tied to Ciphertext)

┌───┐ ┌───┐ │ M │──►(E)──►(||)──► E(K₂,M)||MAC(K₁,E(K₂,M))──►(C)──►Compare──►(D)──► M └───┘ ↑ ↑ ↑ ↑ K₂ K₂ │ MAC(K₁,E(K₂,M)) computed on ciphertext K₁ └─────(C)◄─K₁ Key insight: Encrypt first, then compute MAC on ciphertext. Benefit: Receiver can verify MAC before decrypting — avoids decrypting tampered data.
Configuration (c) is generally preferred in practice: verify integrity first, then decrypt. This is the principle behind Authenticated Encryption with Associated Data (AEAD), used in TLS 1.3.
Requirement

Computation Resistance Exam

An attacker knows the MAC function (Kerckhoffs' principle) but not the key K. The MAC function must satisfy:

Computation Resistance: Given one or more text-MAC pairs [xᵢ, MAC(K, xᵢ)] it must be computationally infeasible to compute any new text-MAC pair [x, MAC(K, x)] for any new input x ≠ xᵢ

This is a stronger requirement than just "one-wayness." The attacker should not be able to produce valid tags for any new message, even with many example pairs.

Attack Analysis

Two Brute-Force Attack Vectors Exam

Attack 1 · Brute Force on Key K

1

Attacker knows one message–tag pair [x₁, T₁] where T₁ = MAC(K, x₁)

2

Key size is k bits → try all 2k possible keys

3

Problem: many keys may produce tag T₁ for this particular x₁ (many-to-one function)

4

For keys that produce T₁, try again with [x₂, T₂] to filter further

∴

Effort to identify correct K ≈ 2k

Attack 2 · Brute Force on MAC Tag

1

Attacker wants to forge tag T_m for a new message x_m without knowing K

2

Tag T has n bits → 2n possible tag values

3

This is analogous to a one-way / weak collision resistance attack on hash functions

∴

Effort to forge a valid tag ≈ 2n

Security Bound

Total Effort to Break a MAC Key

An attacker will always choose the easier of the two attacks:

Effort to break MAC = min(2^k, 2^n) k = key size in bits n = MAC tag size in bits To achieve security level of 2^s: → need both k ≥ s AND n ≥ s Common values used in practice: HMAC-SHA256: k = 256 bits (key), n = 256 bits (tag) → min(2^256, 2^256) = 2^256 HMAC-SHA1: k = 160 bits, n = 160 bits → min(2^160, 2^160) = 2^160 Weak case: k = 128 bits, n = 32 bits → min(2^128, 2^32) = 2^32 ← bottleneck is tag!
A short MAC tag is the bottleneck even if you have a very long key. A 32-bit tag gives only 232 ≈ 4 billion guesses — trivially brute-forceable on modern hardware. NIST recommends at minimum 64-bit tags (preferably 128+ bits).

Cryptanalysis

Algorithm-Specific Attacks

Beyond brute force, cryptanalysis exploits structural weaknesses in specific MAC algorithms. Key points from the slides:

→

Different MAC algorithms are vulnerable to different algorithm-specific attacks. There is no single universal cryptanalytic attack against MACs.

→

MAC algorithms that have survived peer review and standardisation are generally considered secure (security is a property of the algorithm, not just the key).

✓

HMAC has a formal security proof: its security reduces to properties of the underlying hash function (collision resistance, pseudorandomness). This is a significant advantage over ad-hoc constructions.

HMAC

Hash-Based MAC Exam

HMAC constructs a MAC from a cryptographic hash function (MD5, SHA-1, SHA-256, etc.). Hash functions are fast in software and widely implemented in libraries — making HMAC very practical.

The HMAC Formula Must Memorise

HMAC(K, M) = H( (K ⊕ opad) || H( (K ⊕ ipad) || M ) ) Where: H = cryptographic hash function (MD5, SHA-1, SHA-256, …) K = secret key (padded/truncated to block size b) M = message input ipad = 00110110 repeated (inner padding, 0x36 per byte) opad = 01011100 repeated (outer padding, 0x5C per byte) || = concatenation ⊕ = XOR

Step-by-Step Construction

1

Prepare the key K: If |K| > b, hash it: K = H(K). If |K| < b, zero-pad on right to length b.

2

Inner key: Compute K ⊕ ipad (XOR every byte of padded K with 0x36 = 00110110₂)

K_inner = K XOR ipad (= K XOR 0x3636...36)
3

Inner hash: Prepend inner key to message, hash it:

inner = H(K_inner || M)
4

Outer key: Compute K ⊕ opad (XOR every byte of padded K with 0x5C = 01011100₂)

K_outer = K XOR opad (= K XOR 0x5C5C...5C)
5

Final HMAC: Prepend outer key to inner hash, hash again:

HMAC(K, M) = H(K_outer || inner) = H( (K ⊕ opad) || H( (K ⊕ ipad) || M ) )
Why two hash rounds? A naive "H(K||M)" is vulnerable to length-extension attacks. The nested structure prevents this. ipad and opad are different constants to ensure K_inner ≠ K_outer, creating two independent hash instances.

ipad vs opad — Why These Constants?

ConstantHex Value (per byte)BinaryRole
ipad0x3600110110Inner padding — mixed with key for first hash pass
opad0x5C01011100Outer padding — mixed with key for second hash pass

Note: ipad XOR opad = 0x36 XOR 0x5C = 0x6A = 01101010₂. They differ in 4 of 8 bits, providing adequate separation between the two key variants.

Security of HMAC: HMAC's security is entirely dependent on the security of the underlying hash function H. If H is collision-resistant and pseudorandom, HMAC is a secure PRF. This means: use HMAC-SHA256, not HMAC-MD5 (MD5 has known collision vulnerabilities).
